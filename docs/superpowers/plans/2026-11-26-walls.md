# Walls Stage — Walls, Gates, Towers Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The player can drag stone walls, place gates peasants walk through, and raise towers.

**Architecture:** `src/sim` gains three object kinds (Wall, Gate, Tower) in the `OBJECT_KINDS` table, a rock flag and a steepness floor in the placement rules, gate walkability, a Bresenham line helper and a `placeWallLine` command. `src/render` gains three shapes and an instanced wall-line ghost. `src/input`, `src/game` and `src/ui` gain press/release events, a wall drag in the build controller, three tools and a cost readout.

**Tech Stack:** Node 26, TypeScript 7 (strict), Vite 8, Three.js 0.187, Vitest 5.

**Spec:** `docs/superpowers/specs/2026-11-26-walls-design.md` — read it before starting any task.

## Global Constraints

- Project root: `D:\Projekty\warriors-and-cavalry`. Work on branch `walls`. Never push; never touch `main`.
- `AGENTS.md` is binding: layers (`tests/layers.test.ts`), simulation purity (`tests/simPurity.test.ts`), one class per file, explicit modifiers and return types, doc comments on public methods, named interfaces for data, no `enum`, files under about 150 lines, no new dependencies, no asset files.
- Authorship: commits carry no `Co-Authored-By` trailer and no AI or tool attribution of any kind.
- The world changes only through `World.apply(command)` and `World.tick()`; commands and results are plain data. Render, UI and game code only read the world.
- Numbers live in data: costs, footprints and the rock flag in `OBJECT_KINDS`; the 64-tile line limit and the 0.6 slope floor as named constants in `src/sim`.
- Small commits; `npm test` and `npm run build` pass on the last commit of every task.

## Review Focus

1. **A drag that starts or ends off the map, or on water** — the line is still computed from the tiles that are on the map; off-map tiles count as skipped; nothing throws. (Task 1 test, Task 3 test.)
2. **Releasing the button outside the canvas or after the tool changed mid-drag** — no wall is built from a stale start tile; the ghost disappears. (Task 3 test.)
3. **A wall drawn across a walking peasant's path or around a working building** — peasants re-route or report `worker cannot reach`; nothing throws. (Task 1 test.)
4. **A gate placed where peasants already stand, or a wall over a standing idle peasant** — the existing "start tile exempt" and idle-stand rules keep them moving. (Task 1 test.)
5. **Many wall pieces** (a 64-piece drag, a few hundred pieces on the map) — the ghost does not create meshes per frame, and the frame rate stays about the same. (Task 3 test and browser check.)

**Interfaces:**
- Produces:
  - `ObjectKind` gains `Wall: 9`, `Gate: 10`, `Tower: 11`. `ObjectKindInfo` gains `rockAllowed: boolean` (true only for these three). Table values: Wall 1 × 1, cost `resources(0, 2, 0)`; Gate 1 × 1, cost `resources(0, 6, 0)`; Tower 2 × 2, cost `resources(0, 20, 0)`; names `Wall`, `Gate`, `Tower`; all buildable, no storage, production or housing.
  - Placement: terrain passes on `Rock` for `rockAllowed` kinds (in addition to Grass/Sand); `MIN_SLOPE_LIMIT = 0.6`, limit = `max(MIN_SLOPE_LIMIT, SLOPE_PER_TILE × longer side)`.
  - `ObjectIndex.isWalkable`: a Gate tile is walkable (like a Tree tile).
  - `WALL_LINE_MAX_TILES = 64`; `wallLineTiles(from: TileCoord, to: TileCoord): TileCoord[]` — Bresenham from `from` to `to` inclusive, cut to the first 64 tiles. Integer-only, pure.
  - `WorldCommand` gains `{ readonly type: 'placeWallLine'; readonly fromTx: number; readonly fromTy: number; readonly toTx: number; readonly toTy: number }`.
  - `CommandResult` success gains the variant `{ readonly ok: true; readonly placed: number; readonly skipped: number; readonly unpaid: number }`; the existing `{ ok: true; object }` stays for the other commands.
  - `World.apply(placeWallLine)` follows the spec exactly: walk the tiles; a tile failing `canPlace(Wall, …)` (including off-map) is skipped; a valid tile is placed and pays 2 stone; at the first valid tile that cannot be paid for, stop and count it and the remaining valid tiles as `unpaid`; when nothing was placed, fail with `NotEnoughResources` if any tile was valid, otherwise with the first tile's rule reason, changing nothing.
  - `World.previewWallLine(from: TileCoord, to: TileCoord): WallLinePreview` with `interface WallLinePreview { readonly tiles: readonly TileCoord[]; readonly placeable: readonly boolean[]; readonly placedCount: number; readonly cost: ResourceAmounts }` — the same walk without changing anything, so the ghost and the command cannot disagree. (`placeable[i]` is true only for tiles the command would place.)

**Interfaces:**
- Consumes: the new kinds from Task 1.
- Produces:
  - `type GatePassage = 'northSouth' | 'eastWest'`; `BuildingMeshFactory.create(kind: ObjectKind, passage?: GatePassage): THREE.Mesh` — `passage` matters only for a Gate (default `'eastWest'`).
  - Shapes, one merged vertex-coloured mesh each, same conventions as the other buildings (origin at the footprint's lowest corner, floor at `y = 0`, foundation to `y = -1.5`): Wall — a block filling its tile (no 0.15 margin, so neighbours join), about 1.6 tall, with crenellations; Gate — the same block with an opening at least 0.5 wide through it along the passage direction; Tower — 2 × 2, about 3 tall, crenellated. Stone colours from the existing palette.
  - `BuildingLayer` decides a new Gate's passage when it creates its mesh: `'northSouth'` when the tile west or east of the gate holds a Wall, Gate or Tower, otherwise `'eastWest'`; not recomputed later.

  - `TileHover` (or the per-frame hover code) shows the wall ghost instead of the single-building ghost while a drag is active, and the HUD message line shows `Wall: 12 pieces, 24 stone` (pieces = `placedCount`, stone = cost) while dragging.
